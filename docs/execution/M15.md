# M15 — Identity, projection, transform contracts, and Phase 1 boundary ADRs (v4 §§8, 14, 19, 119–125)

**Status:** work order — 2 weeks. Authored at the M12 gate. The executor
implements mechanically; deviation = amendment or discovered gap, never silent.

## Scope

Publish identity/version semantics, projection levels and lens laws, and the
eight-field transform-contract model as normative data. Resolve Phase 1's source
grammar and incremental-engine boundaries through explicit T1 ADR checkpoints.
This order does not build the production CST, query engine, transform runtime,
macros, or compiled Jurisdiction optimization (`docs/implementation-plan.md` §4
items 1, 3, 9, 12).

## Spec inputs

v4 §§8–20, §24, §112–114, §118A, §§119–125; ADR-0009, ADR-0010, ADR-0011;
M07, M08, M09, M10, and M12.

## Frozen surfaces

ADR-0009 grade ceilings, ADR-0010 M09 Level 2/M10 Level 1 declarations, all
eight `TransformContract` field names, projection law names, canonical v4 files,
and Phase -1 goldens. No capability level may increase without new measurement.
No parser or query-engine implementation begins before its required accepted ADR.

## Pre-made decisions

- **D15.1 —** entity identity and immutable version identity remain separate;
  heuristics never prove logical continuity.
- **D15.2 —** projection claims are per supported subset and direction. No
  universal bidirectional promise is expressible.
- **D15.3 —** `TransformContract` remains data with exactly eight §14 fields;
  Phase 0 freezes JSON field names but not Phase 3's future typed atom vocabulary.
- **D15.4 —** interim graph interchange is stable debug JSON only. No final binary
  serialization is selected before migration evidence (v4 §121).
- **D15.5 —** interpretive Jurisdiction, RepairPlan, Basis selection, and ILRP stay
  reference oracles. Compiled plans remain forbidden until differential evidence
  satisfies §125.
- **D15.6 — T1 RESERVED DECISION:** source grammar choice among §119's three
  alternatives requires explicit user acceptance of its ADR before CST work.
- **D15.7 — T1 RESERVED DECISION:** Salsa versus a Liminal-specific revision
  engine requires explicit user acceptance of its ADR before Phase 1 tracked
  query work. Required boundaries in §122 are non-negotiable under either choice.

## Data schemas

`spec/fixtures/transform-contract.schema.json` is JSON Schema draft 2020-12:
object, `additionalProperties: false`, all eight fields required. `requires`,
`preserves`, `introduces`, `may_discard`, and `required_capabilities` are arrays
of unique non-empty strings; three boolean fields retain exact Rust names.

`spec/fixtures/transform-contract.examples.json` contains `version: 1` and at
least one nondestructive and one destructive example. Destructive means
`may_discard` non-empty and therefore requires explicit acceptance before run.
`liminal-conformance` adds a path dev-dependency on `liminal-transform`. Schema
validation is the exact manual subset above, implemented with serde and explicit
key/type/uniqueness checks; no general JSON-Schema dependency is introduced.

## Algorithms

1. Expand `spec/ir.md`, `spec/syntax.md`, and the identity/projection portions of
   `spec/kernel.md` into self-contained normative chapters. Every promise cites
   a golden measurement or accepted ADR.
2. Serialize live `TransformContract` examples, validate against schema, reject
   unknown/missing/duplicate/empty fields, and round-trip byte-canonical JSON.
3. Draft one ADR per open repository decision: §119 source grammar, §121 interim
   stable debug JSON, §122 engine, and §125 optimization boundary. Source grammar
   and engine ADRs remain proposed until user selects and accepts one outcome.
4. Run a contradiction audit: declared grade/level must equal the accepted ADR
   and must not exceed regenerated Phase -1 evidence.
